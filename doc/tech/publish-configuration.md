## 配置分层

发布配置按可提交性和责任分为三层：

| 层级 | 内容 | 存放位置 |
| --- | --- | --- |
| 组件配置 | 坐标、POM、variant、源码策略 | 模块 `PublishInfo` DSL，可提交 |
| Provider 配置 | 启用目标、仓库 URL/name、Central namespace/type | `PublishRepositories` DSL，可提交 |
| Runtime 凭据 | GitHub token、Central token、GPG key/password | 本机 `.publish/local.properties` 或 CI Secrets，不可提交 |

根目录 Android `local.properties` 不再作为发布运行时配置来源。旧 `publish.*`/`centralPublish.*` 字段只能由配置 Skill 读取并迁移，不能继续作为稳定 API。

## 当前入口

### Codex Skill

- `enter-publish-config`：检查和编辑 `PublishInfo`、`PublishRepositories`、本机凭据模板和 caller workflow；可以运行 check，但不上传。
- `enter-publish-run`：消费已经完成的配置，执行用户明确选择的发布目标；不修改配置和 workflow。

仓库内 `skills/` 是 source of truth。本机 runtime 目录必须通过以下脚本链接，不直接编辑本机副本：

```bash
./scripts/install-codex-skill.sh
./scripts/install-codex-skill.sh --check
```

### 离线脚本

```bash
scripts/configure-publish-offline.sh :library \
  --component-type library \
  --execution local \
  --publish-target central \
  --check-only \
  --run
```

脚本支持 macOS 和具备 bash/Java/Gradle wrapper 的 Linux。Windows 使用 Git Bash/WSL，或直接运行对应 Gradle task。

`--check-only` 只调用 `:module:checkPublish`；不生成模板、不写 workflow、不写 GitHub Secrets，也不上传 artifact。

`checkPublish` 支持 `-PpublishValidationLevel=structure|credentials|remote`。workflow check-only 使用 structure；本机默认 credentials。manifest 只记录 credential source 类别，不保存用户名或 secret value。

## DSL 示例

```kotlin
PublishInfo {
    groupId = "cn.entertech.example"
    artifactId = "example-library"
    version = "1.0.0"
    pomDescription = "Example library"
    pomUrl = "https://github.com/Entertech/example"
}

configure<custom.android.plugin.PublishRepositories> {
    githubPackages {
        enabled.set(true)
        repository.set("Entertech/example")
    }
    central {
        enabled.set(true)
        namespace.set("cn.entertech")
        publishingType.set("user_managed")
    }
}
```

## 本机凭据

默认文件：

```text
.publish/local.properties
```

示例字段：

```properties
publish.local.githubPackages.username=
publish.local.githubPackages.token=
publish.local.central.username=
publish.local.central.password=
publish.local.central.signingKeyFile=
publish.local.central.signingPassword=
publish.local.central.signingKeyId=
```

文件必须 ignored 且 untracked。signing key file 可以使用 workspace 外路径；任何日志、manifest 或命令参数都不得包含文件内容和密码。

## CI 配置

`.github/workflows/publish.yml` 接收非敏感 workflow inputs，敏感值通过 caller 的 repository/organization Secrets 传入：

- `MAVEN_CENTRAL_USERNAME`
- `MAVEN_CENTRAL_PASSWORD`
- `GPG_KEY_CONTENTS`
- `SIGNING_KEY_ID`
- `SIGNING_PASSWORD`
- `GITHUB_PACKAGES_TOKEN`（可选，默认可使用 `github.token`）

Central/GPG secrets 只注入实际发布 step。主 job 使用 `contents: read`；README 同步 job 单独申请 `contents: write`。

配置流程生成的 caller workflow 必须包含固定标记：

```text
# Generated by PublishPlugin one-click publish
```

回退或清理逻辑只能自动处理带有该标记的 workflow，不能删除用户手写文件。

## 解析优先级

字段的精确 resolver 略有差异，整体规则为：

```text
命令行 -P 参数
  > Gradle project property
  > 环境变量
  > 可提交 DSL
  > .publish/local.properties
  > 默认值或安全推导值
```

版本优先使用 `publishVersion`，其次才是显式 `version` 与 `PublishInfo.version`。SCM/POM URL 可以从当前项目 Git remote 或 CI repository 推导，但多个 GitHub remote 有歧义时必须显式配置。

## 旧配置迁移

| 旧入口 | 当前入口 |
| --- | --- |
| `:module:generatePublishConfig` | `enter-publish-config` 或离线脚本 |
| `:module:configurePublish` | `enter-publish-config` |
| `:module:rollbackPublishSecrets` | 通过 `gh secret` 明确处理；配置 Skill 提供迁移/轮换建议 |
| 根目录 `local.properties` 的发布字段 | 非敏感字段迁入 DSL；凭据迁入 `.publish/local.properties` 或 CI Secrets |
| `PublishLibraryRemoteTask` + `publishTarget` | 组件类型 + 目标的显式 task |
| legacy runtime publish skills | `enter-publish-config` 与 `enter-publish-run` |

旧 task implementation 可能仍存在于源码中以帮助迁移，但插件不会注册它们。文档、脚本和新项目不得把这些类当作正式入口。

## Git 与 Secret 安全

配置流程在可能写 secret 前必须：

1. 检查配置文件未被 Git 跟踪。
2. 扫描 tracked files 中明显的发布 secret key 名。
3. 显示 GitHub CLI 当前身份和目标 repository，不显示 secret value。
4. 对覆盖和删除操作采用显式选择；dry-run 只显示名称和路径。

如果 secret 已经提交或 push，仅从当前文件删除并不安全。必须先轮换 credential，再根据团队策略执行 history rewrite；`git replace` 不能清理远端历史。

## 支持边界

- Windows 原生 PowerShell 入口尚未提供；支持 Git Bash/WSL 或直接 Gradle task。
- legacy rollback task 不再公开。Secret 删除/轮换属于显式运维操作，不由发布插件自动执行。
- 文档一致性脚本覆盖公开任务、版本、workflow 和 Skill 固定事实；自由文本语义仍依赖代码评审。
